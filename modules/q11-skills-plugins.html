Q11

技能与插件 —— 能执行 shell 的提示词

1,494 字 · 120 行代码 · 7 块 · 约 14 分钟

Skill 是什么？一句话：一段可以带 shell 命令的提示词。

它不是工具（不返回结构化结果），也不是记忆（不是常驻背景）。 它是一份模板，激活后展开成用户消息塞进对话。

本章拆它的展开过程，以及那个最危险的能力： Skill 体内的 shell 命令会在激活时立即执行。

一、SkillManager 的两类技能

SkillManager（packages/core/src/skills/skillManager.ts:401，1,317 行） 管两类技能：

类型 来源 例子
内置（bundled） 代码内注册 loop batch debug verify simplify
外部（filesystem） 文件系统扫描 用户目录、项目目录、插件

内置技能有 14 个源文件（skills/bundled/，不含测试）：

text
batch.ts        debug.ts       index.ts       loop.tsloop-md.ts      mcp-config.ts  memory-types.tsquest.ts        remember.ts    run.ts         simplify.tsverify.ts       workflow-authoring.ts  run-skill-generator.ts

它们不是 markdown 文件，而是 TypeScript 模块。 registerBundledSkill（:379）把模块注册进管理器。

两类技能的差别不只在来源，还在能力：

  • 内置技能可以调 skill.getBody 动态生成正文（:180）；
  • 外部技能走模板替换与 shell 注入。

三、shell 注入：最危险的一段

executeShellInjection（:239-）把 Skill 正文里的 shell 命令执行掉， 把输出替换回正文。每个命令的逻辑（:246-280）：

ts

五个防护点，逐个看：

防护 值 作用
权限检查 shellPermissionCheck 每个命令单独过权限
超时 30 秒 单个命令不许卡死
pager: 'cat' 禁用分页器 否则命令会挂在 less 里
preventCwdChanges: true 禁止改工作目录 防止污染后续命令
错误抛异常 throw 不静默忽略失败

pager: 'cat' 这条最容易漏。如果不设，某些命令会自动用分页器输出， 在非交互环境里会挂住直到超时。

preventCwdChanges 这条也有意思——Skill 里的命令不该改变会话的工作目录， 否则后面所有工具的相对路径都错位。

四、元数据标签：技能怎么被识别

buildSkillMetadataTags（:147-161）生成三行标签：

ts
const parts = [  `<${COMMAND_MESSAGE_TAG}>${skillName}</${COMMAND_MESSAGE_TAG}>`,  `<${COMMAND_NAME_TAG}>${skillName}</${COMMAND_NAME_TAG}>`,];parts.push(`<${SKILL_FORMAT_TAG}>true</${SKILL_FORMAT_TAG}>`);return parts.join('\n');

三行 XML 标签，作用是让下游能识别「这条消息来自技能」：

  • command-name —— 路由用；
  • skill-format: true —— 标记这是技能展开的正文。

斜杠命令走另一条路（:152-154 调 buildSlashCommandMetadata）， 因为斜杠命令有参数需要保留。

五、基目录为什么不算权限

buildSkillPromptContent（:225-234）只做一件事——把基目录写进正文：

ts
export function buildSkillPromptContent(  skill: SkillDefinition,  skillBody: string,): string {  if (skill.isBuiltin || isWorkflowSkill(skill)) {    return skillBody;  }  return `Base directory for this skill: ${skill.skillRoot}\n\n${skillBody}`;}

注释（:220-224）说明了一个关键点：

A filesystem-backed skill's base directory is resource-location metadata, not a filesystem permission grant. Built-in skills are programmatic and have no resource root to expose.

也就是说：正文里写着「基目录是 /some/path」， 不等于模型可以随意读这个目录下的文件—— 读文件还是要过 Read 工具的权限检查。

这个区分很重要。如果实现时把它当成权限授予， 一个恶意 Skill 只要声明基目录为 / 就能读遍全盘。

七、工程暗坑

1. disableSkillShellExecution 只对外部技能生效 :207 的条件是 config.isSkillShellExecutionDisabled() && !skill.isBuiltin。 内置技能豁免——因为它们的正文是代码生成的，不受外部输入影响。 自定义技能时如果想让内置技能也不执行 shell，得自己加逻辑。

2. 权限检查是逐命令的，不是逐技能 shellPermissionCheck(command, executionShell) 每个命令调一次。 一个技能里有 5 条命令，就要过 5 次检查。 漏掉一次检查，就等于给这个技能开了后门。

3. 30 秒超时是硬限制 AbortSignal.timeout(30_000) 写在代码里，没有走配置。 技能里不能跑长时间的命令（比如 npm install）。 需要长任务就走 Shell 工具，那有独立的超时策略。

4. 命令失败必须抛，不能返回空串 :275-279 抛异常。如果改成返回空字符串， 模型会看到正文里「命令输出」的位置是空的， 然后基于缺失信息继续推理——错误会在下游放大。

5. 基目录不是权限授予 见第五节。把它当权限是安全漏洞。

6. 子代理深度检查防止无限嵌套 :190-192 在深度超限时过滤掉 Agent 工具。 如果自定义技能生成逻辑时不检查，会做出「技能套技能套技能」的递归。
